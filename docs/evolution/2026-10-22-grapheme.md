## Candidate priorities and demand evidence

| Candidate | Evidence and current gap | Acceptance / compatibility cost | Decision |
| --- | --- | --- | --- |
| Explicit grapheme mode | [diff-match-patch #59](https://github.com/google/diff-match-patch/issues/59) describes emoji corruption in a message revision log. Current default locally reproduces split surrogates. | Headless marks/attrs comparison | Current text comparison takes new marks on unchanged text; document reconstruction retains old node attrs. | Inline leaf change display | Text-only diff marks leave images and hard breaks without visible change annotations. | Attribute changes and inserted/deleted leaves must be observable with schema-valid rendering. | Investigate as a consumer of headless results rather than forcing every schema into a mixed document. |

The upstream emoji report is evidence of a real use case, not proof of current
upstream status or a new complaint filed against this repository. The local
reproduction is the evidence for the present default-mode behavior.
[PR #1](https://github.com/hamflx/prosemirror-diff/pull/1)'s word-diff request
was already addressed in the July implementation; it is not an open unmet need.

[Tiptap Compare](https://tiptap.dev/docs/compare/getting-started/overview) already
offers headless comparison without an editor instance, on client or server.
Those capabilities are not a unique proposed advantage here. The structural
discussion motivates an external result model, not a complete collaborative
review engine in this batch.

## API research and implementation choice

[TC39's segmentation explainer](https://github.com/tc39/proposal-intl-segmenter)
distinguishes code points from graphemes. [jsdiff's character API](https://github.com/kpdecker/jsdiff#api)
uses code-point tokens, which still do not keep multi-code-point emoji or
combining sequences intact. Reuse the existing bundled UAX #29 grapheme
segmenter and bounded diffArrays implementation instead of adding a dependency.
ProseMirror text offsets remain UTF-16 offsets, so mark restoration continues
to use string lengths, not token counts.

Local reproduction of the default dependency:

```js
new diff_match_patch().diff_main('😉', '😀')
// [[0, '\ud83d'], [-1, '\ude09'], [1, '\ude00']]
```

Add `{level: 'grapheme'}` to the existing document/text entry points and export
`diffGraphemes(oldText, newText)`. It returns `{type, text, level}` segments,
aligns graphemes across the complete text run and preserves input code units
without normalization. The word refinement helper is reused with explicit
level labels; its old default labels and fallback behavior are unchanged.
Default char mode remains unchanged for compatibility.

## Acceptance and limits

- Whole-cluster edits for surrogate-pair emoji, modifiers, ZWJ emoji, flags,
  combining accents and Indic clusters.
- Exact reconstruction for empty strings, CRLF, CJK, canonically equivalent
  but differently encoded inputs and isolated surrogates.
- 200 deterministic mixed-script input pairs check reconstruction and boundaries.
- Edit-budget and simulated-deadline fallbacks preserve complete graphemes.
- Document integration preserves source marks with UTF-16 offsets, whole-text
  and whole-block changes, and schemas that omit the optional level attribute.
- Existing marked-node boundaries can split a cluster in the output: formatting
  is preserved rather than silently merged. Helper segments remain whole-cluster.
- The one-second deadline bounds diff search, not segmentation or all work;
  tokenization remains proportional to input size. It is not a hard realtime API.
- Structural nodes retain existing limitations. This is not a marks/attrs
  change-reporting API or a schema-independent structural comparison solution.

## Informational mode comparison

`test/benchmark-grapheme.mjs` prepares inputs outside timing, then runs each
mode sequentially with 3 warmups and 15 measured calls. Median is sorted sample
7; p95 is sample 14. Timed work includes diff computation and output construction,
not input repeat() calls. Node v24.19.0, same process and inputs for each mode.

| Case | char median / p95 ms | word median / p95 ms | grapheme median / p95 ms |
| --- | ---: | ---: | ---: |
| short emoji | 0.016 / 0.051 | 0.091 / 0.303 | 0.028 / 0.149 |
| prose ~2k | 0.008 / 0.017 | 1.690 / 5.378 | 0.353 / 1.056 |
| repeated Unicode edits | 1.815 / 2.488 | 3.695 / 6.775 | 2.630 / 3.577 |
| unrelated 1001 clusters | 403.461 / 1000.855 | 322.815 / 352.457 | 320.353 / 346.187 |

These modes have different semantics and are not interchangeable outputs.
This single-run measurement is not a general speedup claim or CI threshold.
Repeat across processes before drawing performance conclusions. The purpose
of grapheme mode is predictable Unicode edit boundaries, not lower latency.
